How to use this document

This specification is written for direct use by an AI developer agent and a cross-functional delivery team.

• Requirements are atomic and have stable IDs.

• Business rules have `BR-` IDs.

• Acceptance criteria have `AC-` IDs and use Given/When/Then form.

• Build in the order given in Section 4.

• Anything marked **Out of scope** must not be built for this MVP.

• Do not invent bank-specific values, APIs, capacity rules, thresholds, or compliance approvals.

• Where a value is marked `TBD`, keep it as configuration and record the decision in `DECISIONS.md`.

• If a requirement is ambiguous, choose the simplest behaviour that satisfies the acceptance criteria, record the choice in `DECISIONS.md`, and continue.

• Do not use real customer data, production credentials, or live banking integrations.

• The AI output is advisory. An employee must approve or override it before a booking is confirmed.

The implementation team may use a deterministic mock classifier or a real approved AI model behind the same interface. The demo must demonstrate the end-to-end behaviour without claiming production model accuracy.

1. Overview

System X currently assigns booking duration before the actual case complexity is known. Simple matters may consume a standard slot, while apparently short bookings may overrun into the next appointment.

The MVP demonstrates an AI-assisted booking-triage flow:

1. A customer or employee enters a natural-language case description.

2. System X retrieves relevant synthetic customer/system context.

3. A triage service identifies the case type and estimates complexity and handling time.

4. System X recommends a capacity category:

   - **Quick case:** 2–5 minutes

   - **Standard case:** 10–15 minutes

   - **Complex case:** 20–30+ minutes

5. An employee reviews the recommendation.

6. The employee approves or overrides it.

7. System X checks simulated capacity and confirms a simulated booking.

The demo solves a capacity-matching problem. It does not make a financial, credit, fraud, eligibility, or access decision.

1.1 Primary goal

Demonstrate a complete, credible, testable booking journey in which the current case description and relevant context affect the recommended duration and capacity.

1.2 Key demo message

> System X helps route the right case to the right amount of time, while the employee remains in control of the final booking.

1.3 Definitions

| Term | Meaning |

|---|---|

| Case | A customer request submitted for booking triage. |

| Case description | Natural-language text describing the customer’s need. |

| Triage | Classification and estimation performed before booking. |

| Quick case | A well-defined case recommended for a 2–5 minute slot. |

| Standard case | A normal case recommended for a 10–15 minute slot. |

| Complex case | A case likely to require investigation, verification, or additional work; 20–30+ minutes. |

| Capacity pool | A simulated pool of appointment slots for a category. |

| Recommendation | The triage result proposed to the employee. |

| Override | A change made by the employee to the recommended category or duration. |

| Booking | A simulated reservation of a capacity slot. |

| Synthetic data | Fictional data created for the demonstration. |

| Low confidence | A result that cannot safely be used without employee review or fallback. |

2. Confirmed scope facts

The following facts are confirmed by the business input:

• System X is used for customer and employee bookings.

• Current appointment duration is commonly standardised, typically around 15 minutes.

• Some simple cases take approximately 2–5 minutes.

• Some short bookings become broader discussions.

• Complexity is often discovered when the meeting starts.

• The mismatch can create unused capacity, overruns, delays, lower productivity, and additional meetings.

• The future flow should use a natural-language case description.

• Relevant system context may include:

  - Recent customer/system changes

  - Information completeness

  - Existing mandates or powers of attorney

  - Similar action history

  - Likelihood of additional actions

• The employee must be able to review and override the recommendation.

• BankID is a representative normally short and well-defined case and must be included as a quick-case scenario.

The following are **not confirmed** and must remain configurable or be recorded as decisions:

• Exact System X production APIs.

• Exact business taxonomy beyond the demo scenarios in this document.

• Real-world duration distributions.

• AI model, provider, prompt, or hosting environment.

• Confidence thresholds.

• Workforce capacity rules.

• Regulatory or model-risk approval.

3. Goals, non-goals, and success criteria

3.1 In scope

• Synthetic customer and system context.

• Natural-language case input.

• Repeatable demo scenarios.

• Case-type classification.

• Complexity classification.

• Handling-time band.

• Capacity recommendation.

• Explanation and confidence status.

• Human review and override.

• Simulated capacity availability.

• Simulated booking confirmation.

• Structured demo event/audit record.

• Automated tests for the complete flow.

3.2 Out of scope

Do not build these for the MVP:

• Real customer personal data.

• Live customer authentication or live BankID authentication.

• Production System X integration.

• Production calendar or workforce scheduling.

• Credit, fraud, AML, KYC, eligibility, pricing, or financial decisions.

• Automatic rejection or restriction of a customer service.

• Automated booking without employee approval.

• Real customer email/SMS notifications.

• Model training on production data.

• Production monitoring, model governance, or regulatory certification.

• Native mobile application.

• Multi-language support unless separately approved.

• A claim of production-level accuracy or business benefit.

3.3 MVP success criteria

The MVP is successful when:

1. A user can complete the flow from case description to simulated booking.

2. BankID is recommended as Quick case with a 2–5 minute duration.

3. A standard case is recommended as Standard case with a 10–15 minute duration.

4. A complex case is recommended as Complex case with a 20–30+ minute duration.

5. The current description, not stale previous state, drives the result.

6. The employee can override the result with a reason.

7. Ambiguous cases receive a safe fallback or employee-review status.

8. A failed triage or availability check cannot produce a confirmed booking.

9. All scenarios use synthetic data only.

10. The team can explain which outputs come from AI interpretation, deterministic rules, and simulated integration.

8. Business rules and safety rules

These rules define MVP behaviour. Thresholds and taxonomies are configuration, not hard-coded bank facts.

| ID | Rule | Priority |

|---|---|---|

| BR-011 | A BankID help/activation case with complete information and no additional action shall default to `quick`. | Must |

| BR-012 | A clearly scoped information-only question with no action required shall default to `quick`. | Must |

| BR-013 | A straightforward payment/transfer with complete context and a similar previous action shall default to `quick`. | Must |

| BR-014 | A normal account-change case with partial information or possible additional work shall default to `standard`. | Must |

| BR-015 | Missing information or documents shall prevent automatic quick-case routing. | Must |

| BR-016 | Mandate/power-of-attorney verification combined with a recent change shall default to `complex` or employee review. | Must |

| BR-017 | Descriptions indicating investigation, dispute, complaint, multiple actions, or unusual circumstances shall default to `complex` or employee review. | Must |

| BR-018 | Low confidence shall require employee review and shall not automatically select quick capacity. | Must |

| BR-019 | Missing or contradictory context shall require employee review or standard fallback. | Must |

| BR-020 | The employee can override any recommendation before booking. | Must |

| BR-021 | A high-risk or uncertain case must not be shortened solely because the text is short. | Must |

| BR-022 | The final booking category is the employee-approved category, not necessarily the AI recommendation. | Must |

| BR-023 | A failed triage, availability, or booking operation cannot transition the case to `confirmed`. | Must |

8.1 Classification strategy

Implement the following interface:

```text

CaseClassifier.classify(caseDescription, approvedContext) -> ClassificationResult

The implementation may be:

• A deterministic mock for the first MVP.

• An approved LLM/classifier adapter.

• A hybrid model where AI interprets text and deterministic rules apply safety constraints.

The rest of the system must not depend on a specific model provider.

8.2 Confidence

Use configured statuses:

• `high`

• `medium`

• `low`

Do not invent a numeric threshold. If a numeric score is returned by a model, store it as diagnostic metadata and use configured status mapping.

10. Synthetic data contract

10.1 Dataset principles

• Fictional names, identifiers, dates, and account references only.

• No copied or transformed production records.

• Dataset version stored with every triage result.

• Expected labels separated from model output.

• Include normal, ambiguous, contradictory, and override cases.

• Include a short rationale for every expected label.

10.2 Customer context

```json

{

  "customerContextId": "CUSTCTX-0101",

  "datasetVersion": "v1",

  "recentChange": "none",

  "informationCompleteness": "complete",

  "mandateStatus": "not_relevant",

  "similarActionHistory": "not_relevant",

  "additionalActionLikely": "no"

}

Allowed values:

• `recentChange`: `none`, `within_7_days`, `within_30_days`, `unknown`

• `informationCompleteness`: `complete`, `partial`, `missing`, `unknown`

• `mandateStatus`: `exists`, `missing`, `unclear`, `not_relevant`

• `similarActionHistory`: `yes`, `no`, `not_relevant`, `unknown`

• `additionalActionLikely`: `no`, `possible`, `yes`, `unknown`

10.3 Case record

| Field | Type | Required |

|---|---|---|

| `caseId` | String | Yes |

| `customerContextId` | String | Yes |

| `description` | String | Yes |

| `caseTypeExpected` | Enum | Yes |

| `complexityExpected` | Enum | Yes |

| `durationBandExpected` | Enum | Yes |

| `capacityExpected` | Enum | Yes |

| `expectedReasonCodes` | Array | Yes |

| `expectedConfidenceStatus` | Enum | Yes |

| `overrideExpected` | Boolean | Yes |

| `simulatedOutcome` | Enum | Should |

10.4 Minimum dataset

Create at least:

• 5 BankID quick cases.

• 5 other quick cases.

• 5 standard cases.

• 5 complex cases.

• 3 ambiguous/low-confidence cases.

• 3 expected override cases.

• 2 apparently simple descriptions made complex by context.

• 2 apparently complex descriptions safely classified as quick after context.

• 2 unavailable-capacity cases.

• 2 service-failure cases.

13. State model

13.1 Case/booking states

```text

DRAFT

  -> TRIAGE_PENDING

  -> TRIAGE_READY

  -> EMPLOYEE_REVIEW

  -> SLOT_SELECTION

  -> BOOKING_PENDING

  -> CONFIRMED

Failure states:

```text

TRIAGE_FAILED

AVAILABILITY_FAILED

BOOKING_FAILED

REVIEW_REQUIRED

NO_CAPACITY

13.2 State rules

• A case cannot enter `CONFIRMED` without a valid employee decision.

• A case cannot enter `CONFIRMED` without an available selected slot.

• Editing the description after triage returns the case to `DRAFT`.

• An override changes the final decision but does not mutate the original AI recommendation.

• Failed operations retain diagnostic status and correlation ID.

17. AI safety and human oversight

The following are mandatory:

• The recommendation is advisory.

• Employee review is required before booking.

• Employee override is always available.

• Override reason is captured.

• Low-confidence cases cannot automatically route to Quick case.

• Rules can increase allocated time but cannot silently reduce time for uncertain/high-risk cases.

• Explanations are generated from traceable reason codes.

• The model must not infer or display unnecessary sensitive attributes.

• Prompt/model input and output must be bounded by the approved synthetic schema.

• The model must not call external tools or services beyond approved adapters.

• A deterministic mock must be available for repeatable tests.

• Double booking attempt.

• Triage timeout/failure.

• Context service failure.

• Booking service failure.

• Stale triage after description edit.

19.5 Security-boundary tests

Verify:

• No real-looking customer data in fixtures.

• No sensitive fields returned by context endpoint.

• No stack traces or secrets in errors.

• No booking without employee approval.

• No booking after failed required operation.

19.6 Evaluation metrics

For the synthetic dataset, calculate:

• Case-type agreement.

• Complexity agreement.

• Duration-band agreement.

• Quick-case precision.

• Complex-case recall.

• Fallback rate.

• Employee override rate.

• Booking completion rate.

• Mean and median triage response time.

These are demo evaluation metrics, not production claims.

20. Acceptance criteria

AC-001 — BankID happy path

**Given** a synthetic BankID activation case with complete context  

**When** the user runs triage  

**Then** the result is `bank_id_support`, `quick`, `2_5`, `quick_case`, and employee review is required.

AC-002 — BankID booking

**Given** the BankID result is approved by an employee  

**When** an available quick-case slot is selected and confirmed  

**Then** the booking status is `confirmed` and the confirmation shows 2–5 minutes.

AC-003 — Standard case

**Given** a synthetic account-change case with partial information  

**When** triage runs  

**Then** the result is `standard`, `10_15`, and `standard_case`.

AC-004 — Complex case

**Given** a synthetic mandate case with a recent change and verification required  

**When** triage runs  

**Then** the result is `complex`, `20_30_plus`, and `complex_case` or configured specialist capacity.

AC-005 — Current description controls result

**Given** a user selected BankID  

**When** the user replaces the description with a complex mandate case and runs triage  

**Then** the previous BankID result is invalidated and the complex case is analysed.

AC-006 — Context affects result

**Given** a short description  

**When** context indicates missing information and a recent mandate change  

**Then** the system must not route the case automatically to Quick case.

AC-007 — Explanation

**Given** a completed triage  

**When** the recommendation is displayed  

**Then** at least one traceable reason message is shown and each reason maps to a known reason code.

AC-008 — Low confidence

**Given** the classifier returns low confidence or ambiguous case type  

**When** triage completes  

**Then** `requiresEmployeeReview` is true and Quick case is not automatically selected.

AC-009 — Override

**Given** an employee changes Quick case to Standard case  

**When** the employee supplies an override reason  

**Then** the final booking uses Standard case, the original recommendation remains recorded, and the event records the override.

AC-010 — Missing override reason

**Given** an employee selects a different category  

**When** no override reason is supplied  

**Then** booking is blocked and a field-level error is shown.

AC-011 — No capacity

**Given** no slot exists for the final category  

**When** the employee attempts to continue  

**Then** the system shows `NO_CAPACITY` and does not confirm a booking.

AC-012 — Triage failure

**Given** the triage service fails  

**When** the user attempts to continue  

**Then** the system shows an actionable error, records `triage.failed`, and does not show a successful recommendation.

AC-013 — Booking failure

**Given** booking confirmation fails  

**When** the employee submits the booking  

**Then** the UI shows booking failure and the case is not shown as confirmed.

AC-014 — Synthetic-data boundary

**Given** any demo request, response, fixture, or event  

**When** data is inspected  

**Then** only approved synthetic data and identifiers are present.

AC-015 — Reset

**Given** a completed or failed case  

**When** the user starts a new case  

**Then** all previous case, recommendation, decision, and booking state is cleared.

23. Risks and mitigations

| Risk | Mitigation |

|---|---|

| AI output is inconsistent | Use deterministic mock for repeatable scenarios and keep rules outside the model. |

| Short text is incorrectly treated as simple | Apply context and safety rules before selecting Quick case. |

| Demo is mistaken for production readiness | Use persistent disclaimer and explicit non-goals. |

| Real data enters fixtures or prompts | Synthetic-data review and repository scan before demo. |

| Capacity semantics are wrong | Keep capacity labels configurable and confirm with business owner. |

| Employee does not trust output | Show traceable reasons and allow override. |

| Free-form explanations hallucinate facts | Render reason codes from structured decision evidence. |

| Service failure creates false confirmation | Enforce state transitions and negative tests. |

| Team components do not integrate | Agree contracts and enums before parallel implementation. |

| Metrics are overinterpreted | Label all results as synthetic/demo evaluation. |
